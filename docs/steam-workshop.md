# Steam Workshop

## Subscription performance

Filtering, de-duplication and ordering run on `Dispatchers.Default`. Before publishing a computed page, the ViewModel checks the query generation, list identity and subscription mutation version. If details or a subscription action changed the list during processing, it recomputes from current state; cancelled searches cannot publish stale rows.

Pagination merges a small sorted page into the existing ordered list. When all matching subscriptions have been loaded, changing only the sort reorders the existing data without fetching the same pages again. Explicit refresh and changed search/tag filters still read Steam.

For a full reorder of at least 1,024 items, the optional Rust core sorts numeric metadata in one JNI call. Only scores and canonical unsigned published-file IDs cross the boundary. Kotlin validates the returned index permutation and maps it back to the original models. Descending scores, lexicographic decimal ID tie-breaks and stable duplicates match Kotlin. Small lists, non-canonical IDs, unavailable/older libraries or invalid native results use Kotlin. Already ordered lists return immediately. Account authentication and subscription writes use the existing Kotlin services.

The host benchmark includes array preparation, JNI, native sorting, permutation validation and result-list construction. Build and run it with:

```shell
cargo build --manifest-path rust/Cargo.toml --release --locked -p monica-steam-android
./gradlew :app:benchmarkWorkshopSubscriptions -PsteamNativeTestLibraryDir=../rust/target/release
```

It checks parity and reports median/p95 timings for 30, 256, 1,024 and 10,000 items after warmup, alternating implementations on identical deterministic data. These are host CPU measurements, not Android frame-rate or network latency measurements. Native and fallback regression tests run in the existing Steam CI matrix.

Measured on the development Windows/JDK 17 host with the release Rust library:

| Subscription count | Kotlin median | Optimized median | Kotlin p95 | Optimized p95 |
| --- | --- | --- | --- | --- |
| 256 (Kotlin in both paths) | 0.0512 ms | 0.0510 ms | 0.0857 ms | 0.0956 ms |
| 1,024 | 0.3058 ms | 0.1847 ms | 0.7015 ms | 0.5098 ms |
| 10,000 | 2.7341 ms | 1.2471 ms | 3.8246 ms | 2.3950 ms |

## User flow

Library and Store game details expose Workshop when Store category ID 30 is present. The check distinguishes unsupported games from a failed request and caches successful checks for one hour (at most 128 games).

Browse provides debounced search, popular / most subscribed / newest / recently updated sorting, popularity periods, game-declared tag filters (AND), and pagination. My subscriptions is scoped to the selected account and storage source. It supports the same tags, search, and metadata sorting. List position survives opening a detail and returning. Dependencies open their own native details with a parent stack; unavailable dependencies retain official Steam links.

Browse, Subscriptions and Presets use a persistent tab row. Search contains the filter/sort control, with a badge for tags or customized sorting; the count row reports the active order. The list header menu contains multi-selection, code import and refresh. Subscriptions additionally offers sharing all subscriptions and saving them as a preset. Detail pages keep the subscription action in the content and put the official Steam link and refresh in their menu.

A detail shows its preview, author, description, tags, update time, size, subscription count, additional images, and required items. Subscribing an item with dependencies offers “only this item” and “include dependencies”. Unsubscribing requires confirmation and leaves dependencies alone. Steam on the desktop performs installation; Monica manages account subscriptions and never downloads or executes Workshop packages.

## Multiple selection and sharing

The Workshop list supports an explicit selection mode and long-press selection. Selection uses the same floating bottom `SelectionActionBar` as the token page, positioned above the Dock; list padding leaves the last item reachable above both controls. The bar shows the selected count, select-loaded, available batch actions, sharing and exit. “Select loaded items” selects the records already loaded; changing search, tags or tabs clears the selection.

My subscriptions offers batch unsubscription and sharing, with subscription also rejected by the ViewModel. Browse excludes known subscribed or unsupported selections from subscription requests and known unsubscribed selections from unsubscription requests. Actions with no eligible targets are disabled and cannot create an empty queue. Unknown subscription states remain eligible for the worker's authenticated inspection, which also rechecks states changed outside the app. Confirmation counts use the filtered target IDs. Sharing retains all selected IDs. A confirmation identifies the target account; including dependencies is opt-in, and unsubscribing preserves dependencies.

Batch management captures the original storage/account/game identity and submits an application-owned WorkManager queue. It inspects current metadata and subscription status in chunks of 20 and performs writes sequentially with a delay between items. Every write retains the existing Steam state readback. Already matching states are skipped. Progress distinguishes updated, unchanged, unavailable/failed and remaining items. Stop requests finish the current operation before stopping the queue. Login, rate-limit, network and unconfirmed-result failures stop further writes. An explicit retry re-reads the unfinished items before deciding which writes are still required. Removing subscriptions refreshes offset pagination once after the batch.

“Continue in background”, dialog back and outside dismissal hide progress without requesting cancellation. Users can leave the import preview, switch Dock pages, background the app or recreate the Activity while the queue continues. A progress entry on the Workshop page and a notification reopen the original task; notification inspection does not switch the selected Steam account. “Stop remaining items” is a separate action in both the dialog and notification. A waiting queue can be stopped before sending requests, and an active queue finishes its current operation first.

Android execution uses an expedited WorkManager request with ordinary-work fallback and a notification-backed `dataSync` foreground worker. Notification permission denial does not gate execution. A bounded, atomic checkpoint in `noBackupFilesDir/workshop-tasks` stores the source/account identifiers, game, requested item IDs, dependency choice, progress and stop request; no credentials enter WorkManager Data or checkpoint files. Only the hashed task key is passed through WorkManager. Checkpoints are written every metadata chunk and at lifecycle, stop and failure boundaries. System interruption preserves remaining work; restarting re-reads current Steam state, including an item whose write reply was interrupted. WorkManager terminal-state observation also surfaces failures that occur before the worker body starts. Removed or inaccessible accounts require login/retry on their original source and cannot redirect a queue to the currently selected account.

“Share selected” exports the selected IDs. “Share all my subscriptions” reads every page for the current game, ignoring current search/tag filters, and never produces a partial code after a failed page. Known IDs from unavailable subscription records are retained even when those records cannot be shown in the ordinary list.

Codes begin with `MONICA-WS1:`. The portable payload contains only the game ID and ordered, deduplicated unsigned published-file IDs. It uses GZIP and unpadded URL-safe Base64 around a big-endian binary layout: `MWS1` magic, positive int32 game ID, int32 item count, then unsigned 64-bit IDs. No account identifiers, credentials, author text or executable content are included. Input is bounded to 66,000 characters, 5,000 items and 40,012 decompressed bytes; malformed, truncated, unsupported-version or conflicting codes are rejected.

Sharing through Android sends a `monica://workshop/v1/<payload>` link. The constrained manifest route opens a native preview for the encoded game on both cold launch and a new intent. Codes and links can also be pasted through the Workshop menu or the Store browse menu. Opening a code only loads metadata; the user chooses all eligible items or individual items before subscribing. Steam metadata is checked against the encoded game, and unavailable, unsupported or already subscribed items cannot be selected. A share code is a transferable list, not proof of authorship or current Steam availability.

Import previews reserve a floating card above the Dock for the selected count and subscription action. A single List actions menu groups select all, clear selection, save the entire list as a preset and the opt-in dependency setting. Selecting dependencies also shows a persistent hint next to the selected count. Returning from item details preserves the import list position and dependency choice. The share dialog keeps Copy code as its primary action and groups Android sharing and saving a preset in its own menu.

## Named MOD presets

The Workshop page has a Presets entry. Users can save all subscriptions for the current game, save the list in a share-code dialog (including a shared selection), or import a code and save its entire list. Saving an imported list includes its already-subscribed items; the subscription preview's checkbox filtering does not strip them from the preset. Presets support rename, replacement from the current full subscription list, deletion and sharing through the existing `MONICA-WS1` code format. Names remain local; codes retain their game-and-item-only format. Empty presets are not supported by that format.

One Create preset menu offers subscriptions and share-code sources. Each preset card keeps a concise Switch action; sharing, renaming, updating and deletion are grouped in its menu. The switch preview separates additions, removals and retained items into three readable counts while preserving the complete accessible summary and confirmation flow.

The application-owned preset repository stores bounded, atomic per-game catalogs under `filesDir/workshop-presets`. Each record contains a UUID, name, share code and update time. Presets can be reused with another account for the same game and contain no account identity or credentials. Each game supports 100 presets, names of up to 60 characters, and the existing 5000-item code limit. Duplicate names, invalid/cross-game codes and corrupt catalogs are reported; failed writes do not replace the last complete catalog.

Switching first reads the complete unfiltered subscription list and checks the target items. The confirmation identifies the account and shows additions, removals, retained items and the affected item titles/IDs. Unavailable new targets block confirmation. A strict shared reader also protects preset creation and full-subscription export: page numbers, canonical IDs, stable totals, duplicate/empty pages and final collected counts must agree. It preserves known unavailable IDs rather than computing removals from the visible cards or a partial page.

Confirmation submits one persistent WorkManager task with a frozen copy of the preset name, code and original subscription IDs, bound to the original account/source/game. It checks all target items first, subscribes missing items, re-reads the full list before removals, and removes only IDs included in the confirmed original snapshot. Shared items are retained. New subscription failures stop the task before removals. Deleted/private old items can still be removed when their game membership is established by the full authenticated subscription list. Dependencies are not expanded automatically: users should include required dependencies in the preset itself.

Preset checkpoints use schema 2 so an older client cannot interpret mixed operations as one subscribe-only queue. Schema 1 bulk tasks remain readable. A replacement supports up to 5000 target items plus 5000 removals in a bounded 16 MiB checkpoint, including Unicode titles. Per-item direction, preset identity, progress, stop state and final verification survive interruption. Retry rechecks both sets and skips already matching states, including writes accepted by Steam before their replies were interrupted. Notification reopening and retry use the same controller. Editing or deleting the saved preset later does not alter the running task.

The worker rejects subscriptions outside the confirmed snapshot/target set rather than extending the removal list silently. Before removing old items, it confirms every target remains subscribed. After all operations it reads the complete list again and only reports a completed preset switch when it exactly matches the target. A failed final read remains retryable even when the per-item operation count is complete. Stopping or failing can leave a partially changed list; completed operations are retained, and the UI explicitly reports the switch as incomplete. It does not claim an atomic Steam transaction or automatic rollback.

## Data and boundaries

Public browsing reads JSON from Steam Community SSR hydration (`window.SSR.renderContext.queryData`, `workshop_browse`, `declared_tags`). It never executes page scripts. Game IDs, page numbers, result status and item identities are checked before displaying a batch. A changed schema produces a retryable error, not a misleading empty result. Requests use `SteamApiClient` and preserve its redirect and host restrictions. Images use the existing Steam image loader and CDN allowlist.

Authenticated requests use `PublishedFile.<Method>#1` through the existing account-scoped `SteamCmGateway` and protobuf client. These calls do not send a user access token to the key-restricted PublishedFile Web API endpoints:

| Operation | Method |
| --- | --- |
| Subscription pages | GetUserFiles, type=mysubscriptions, appid and captured steamid |
| Item and dependency metadata | GetDetails |
| Current subscription state | AreFilesInSubscriptionList, listtype=1 |
| Subscribe | Subscribe, list_type=1, notify_client=true, explicit include_dependencies |
| Unsubscribe | Unsubscribe, list_type=1, notify_client=true |

Wire fields follow [SteamDatabase Protobufs](https://github.com/SteamDatabase/Protobufs/blob/master/steam/steammessages_publishedfile.steamclient.proto). Subscription writes are followed by a state readback. Ambiguous results leave state unknown and request refresh; duplicate taps cannot issue parallel writes for the same item. Read generations and mutation versions prevent older responses from reverting newer state. Removing a subscription restarts offset pagination so shifted rows are not skipped.

Steam GetUserFiles does not expose text search. Search and non-default subscription sorting therefore scan all filtered subscription pages, progressively showing results and scan progress, with a cancellable delay between pages. The implementation does not pretend that filtering the first page searches the whole subscription library. No speculative server sort names are sent: the server order is lastupdated; alternate ordering uses returned metadata.

Session refresh captures the source handle (including MDBX origin) used when opening the Workshop. Rotation persists to that origin, even if the user later switches accounts or databases. A session failure permits one refresh retry. No tokens or author-supplied raw errors appear in the UI.

The persistent CM connection preserves `SteamApiException` when unwrapping both logon and service response futures. Otherwise a logged-out response becomes an `IOException`, preventing the Workshop resolver from refreshing credentials and obscuring rate-limit or permission failures. The read regression tests exercise actual CM framing and the persistent connection through to the Workshop ViewModel, rather than mocking away this boundary.

`GetUserFiles.startindex` is a one-based item index: with 30 items per page, Steam returns 1 for page 1 and 31 for page 2. Populated pages validate this index; pagination uses the zero-based consumed-row count so a 31st subscription remains reachable. A successful empty CM response may omit zero-valued protobuf fields. Malformed counters or missing totals alongside returned rows remain errors. Unavailable and individual malformed item records are isolated while pagination counts all returned rows; a page containing only malformed success records remains an error, not an empty library.

Persisted Steam diagnostics record the operation, request/decode stage, numeric HTTP/EResult status, response byte count and page counts. They exclude account IDs, credentials, search terms, item contents and server-provided error messages. This separates account/server failures from schema failures when reproducing on a signed-in device.
